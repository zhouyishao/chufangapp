# 家里有菜：从交互原型到可发布 App 总实施计划

> **执行方式：** 后续实施必须使用 `executing-plans` 或 `subagent-driven-development`，按阶段逐项完成。任何阶段未通过验收，不进入下一阶段。

## 1. 目标

以 `docs/prototypes/home-feed-interactive/index.html` 作为已经确认的 C 端产品与交互验收基准，不再继续修改原型；完善 PostgreSQL 数据模型、Express API 和后台管理配置能力，再逐页替换正式 `frontend/` 中的旧 C 端页面，最终形成以下闭环：

```text
后台录入/编排内容
        ↓
PostgreSQL 真实落库
        ↓
Express 统一接口与鉴权
        ↓
正式 uni-app C 端真实展示与交互
        ↓
自动测试、真机验收、灰度发布、监控回滚
```

最终交付不是“能展示的页面”，而是一个可由后台持续运营、用户数据真实同步、核心流程可闭环、可以提交应用市场审核的 App。

---

## 2. 本次审计结论

### 2.1 已有基础，不需要推翻

- 正式 C 端已有 uni-app + Vue 3 工程、37 个路由、统一请求层、全局样式 Token、首页 CMS、菜谱/食材详情、家庭、菜篮、收藏、浏览、添加菜谱等基础页面。
- 后端已有 Express + Prisma + PostgreSQL、51 个模型、App JWT 基础、家庭菜篮鉴权、公开内容接口及首页运营接口。
- 后台已有首页导航、Banner、内容模块、菜谱、食材、水果、调料、饮品、家庭和用户等页面基础。
- 当前正确策略是保留工程与有效服务，按路由逐页替换视图和数据契约，而不是重建技术栈。

### 2.2 当前阻止发布的主要问题

| 范围 | 当前问题 | 发布影响 |
|---|---|---|
| 数据身份 | 除菜篮外，多处用户接口仍信任客户端 `userId` | 存在越权风险，P0 |
| 账号流程 | 注册、重置密码、个人资料部分仍依赖本地模拟 | 无法跨设备使用，P0 |
| 上传 | C 端头像、家庭头像、菜谱图片/视频没有统一真实上传闭环 | 用户内容无法持久化，P0 |
| 偏好 | 当前家庭偏好是一条家庭聚合数据，不足以表达每个成员的喜欢、忌口、过敏及共享范围 | 家庭提醒不可信，P0 |
| 内容契约 | 饮品、步骤媒体、可见范围、关联菜谱等仍有兼容字段或 JSON 字段 | 后台配置难以稳定驱动 C 端，P0/P1 |
| 后台 | 价格、单位、采购、文件、报表等部分页面仍为 mock/占位 | 不能称为真实后台，P0/P1 |
| C 端 | 大页面体积过大，存在硬编码内容、局部假交互和重复实现 | 难维护且容易回归，P0 |
| 测试 | 缺少后台到 C 端的契约测试、正式 C 端 E2E、真机矩阵 | 无法安全发布，P0 |
| 生产工程 | 缺生产部署、对象存储、备份、CI、监控、签名和应用市场材料 | 无法上线，P0 |

### 2.3 当前原型仍需在实施时纠正的遗留项

原型是视觉与交互基准，不代表其中每个遗留监听器都要照搬。正式实现时需要按已经确认的产品决定处理：

- 不做“草稿”入口和草稿功能；原型内残留的“草稿已保存”监听不进入正式 C 端。
- 不做社交聊天；通知仅包含系统活动、家庭聚餐/开饭提醒和必要业务提醒。
- 不做“家里已有”库存功能。
- 不做大面积液态玻璃；只允许在固定底部导航、必要吸顶层或浮层局部使用。
- “买菜模式”不单独建设；挑选方法通过食材名称或详情页进入。
- 首页 Banner 与详情主图尺寸、结构、频道顺序等已经确认的设计约束不得在迁移中擅自改变。

## 3. 总体执行原则

### 3.1 原型冻结

- 原型目录只读，作为验收截图和交互对照。
- 正式代码只在 `frontend/`、`admin-frontend/`、`server/` 落地。
- 任何原型与旧需求冲突，以本计划列出的已确认产品决策和当前项目规则为准。

### 3.2 后台配置的边界

后台负责：

- 内容字段、图片/视频、分类、标签、单位和参考价格。
- 首页频道、Banner、模块顺序、关联内容、展示数量、上下架和跳转。
- 菜谱、食材、水果、调料、饮品的发布、推荐、排序和状态。
- 业务通知、家庭聚会活动的运营配置和发送状态。

后台不得配置：

- 字号、字重、行高、颜色系统和设计 Token。
- 卡片像素尺寸、详情主图比例、底部导航样式。
- 液态玻璃面积、阴影强度、圆角体系等视觉规范。
- 绕过鉴权的接口地址或任意前端脚本。

### 3.3 数据分类

| 数据类型 | 数据来源 | 管理方式 |
|---|---|---|
| 公共内容 | 后台运营录入 | 后台 CRUD、审核、上下架、排序 |
| 首页编排 | 后台运营配置 | CMS 模块、关联内容、发布版本 |
| 用户资产 | C 端用户产生 | 用户本人鉴权访问，后台仅审计/客服查看 |
| 家庭协作 | 家庭成员产生 | 家庭权限控制，后台仅审计/异常处理 |
| 系统通知 | 后台或业务事件产生 | 模板、目标人群、发送记录 |
| 文件资源 | 后台或 C 端上传 | 统一文件服务、引用计数和生命周期管理 |

### 3.4 迁移策略

- 使用“绞杀式迁移”：保留旧路由，逐个页面把旧实现替换为新组件与真实接口。
- 每个页面通过验收后再移除对应旧代码，不整页一次性重写整个 `frontend/`。
- 先做一条完整纵向切片：后台新建菜谱 → 数据库 → API → C 端首页/列表/详情 → 加入菜篮 → 去烹饪。
- 纵向切片通过后，复制成熟模式到食材、水果、饮品和调料。

## 4. 后台配置到 C 端展示映射

| 业务域 | 后台必须配置 | 后端/数据库 | C 端消费位置 |
|---|---|---|---|
| 顶部频道 | 名称、类型、排序、启用状态 | `HomeTopNav` + App Home API | 首页推荐/菜谱/食材/水果/饮品 |
| 频道 Banner | 频道、图片、标题、副标题、跳转、排序、上下架 | `HomeHeroBanner` | 每个频道独立 Banner 轮播 |
| 首页模块 | 标题、内容类型、内容源、关联内容、数量、顺序、状态 | `ContentModule` 及关联项 | 时令果蔬、家常精选、挑选指南等 |
| 菜谱 | 封面/视频、基础信息、用料、图文/视频步骤、小贴士、分类、标签、可见范围 | `Recipe`、`RecipeIngredient`、`RecipeStep` | 列表、详情、烹饪、相关推荐 |
| 食材 | 图片、分类、时令、参考价、单位、挑选、保存、吃法、禁忌、相关菜谱 | `Ingredient` 及价格/关联表 | 频道、分类、详情、菜篮挑选弹层 |
| 水果 | 使用食材统一模型并带水果类型 | `Ingredient.type=FRUIT` 或等价枚举 | 水果频道、分类、详情 |
| 调料 | 使用食材统一内容能力，增加风味、用量、适配菜谱 | 调料类型及关联表 | 分类目录、调料详情、相关菜谱 |
| 饮品 | 基础饮品字段；可调制饮品增加基酒、辅料、器具、步骤、计时 | `Beverage` + 饮品步骤/用料 | 饮品频道、详情、去制作流程 |
| 分类/标签/单位 | 层级、适用内容类型、排序、状态 | 统一字典表 | 后台表单、分类页、详情展示 |
| 推荐关系 | 来源内容、目标内容、推荐类型、排序 | 显式关系表 | 相似菜谱、同食材菜谱、搭配饮品 |
| 文件 | 文件类型、URL、大小、尺寸、时长、来源、状态、引用 | `File` | 所有图片/视频、头像和菜谱步骤 |
| 用户偏好 | 喜欢、忌口、过敏、是否共享家庭 | 用户偏好与共享范围表 | 我的、家庭口味、采购/烹饪提醒 |
| 家庭 | 头像、名称、成员、备注、角色、家庭码 | `Family`、`FamilyMember` | 我的、家庭管理、菜篮切换 |
| 菜篮/采购 | 家庭、来源菜谱、合并食材、数量、单位、完成状态、批次 | 采购批次及明细 | 菜篮食材/菜谱视图、记录 |
| 通知/聚会 | 模板、家庭活动、到场/开饭状态、接收人 | `Notification`、`FamilyEvent` | 消息入口、开饭提醒 |

### 4.1 配置发布规则

- 后台编辑态与发布态分离；C 端只读取已发布版本。
- 上下架和排序修改必须记录操作人、时间和版本。
- 发布后支持回滚到上一版本，避免错误配置立即破坏首页。
- 删除被使用的分类、单位、文件或内容时必须阻止删除或先解除引用。
- 所有 C 端内容接口只返回已发布、未删除、在有效期内的内容。

## 阶段 0：建立发布基线与冻结契约

**目标：** 在任何业务改造前，形成可对比、可回滚的基线。

- [ ] 建立“原型页面 → 正式路由 → 接口 → 数据表 → 后台页面”追踪表。
- [ ] 记录现有 37 个路由、接口清单、Prisma 模型、后台菜单和 mock 数据位置。
- [ ] 标记每个正式页面为：保留、重构、合并、下线、新增。
- [ ] 为现有 API 生成契约快照，禁止后续无版本地修改字段。

- [ ] 确认首发范围、iOS/Android 渠道、应用名称、Bundle ID、Android Package Name 和 DCloud AppID。

- 页面追踪矩阵。

- 发布范围与非目标清单。

- 数据库可恢复，迁移没有破坏性 SQL。

## 阶段 1：数据模型、鉴权与安全边界

**目标：** 先把数据归属和权限做正确，再开发页面。

### 1.1 App 鉴权全面迁移

- [ ] 将“我的菜谱、收藏、浏览、搜索历史、资料、家庭、偏好、上传、通知”等接口全部接入 `requireAppAuth`。
- [ ] 服务端只使用 JWT 的 `sub` 识别当前用户；逐步删除客户端 `userId`。
- [ ] 家庭接口统一校验创建者、管理员、普通成员的权限。
- [ ] 管理员可移除成员、设置/取消管理员、修改成员备注；创建者不可被普通管理员移除。
- [ ] 登录、验证码、重置密码增加频率限制、失败次数限制和审计日志。
- [ ] 生产环境缺少 JWT Secret、数据库地址或存储密钥时必须启动失败，禁止 `change-me-*` 兜底。

### 1.2 数据模型调整

- [ ] 新建个人偏好、忌口、过敏及家庭共享范围模型，替代单条家庭聚合偏好。
- [ ] 新建采购批次和采购明细模型，支持家庭切换、完成状态和采购记录。
- [ ] 新建通知、家庭聚会/开饭事件及接收记录模型。
- [ ] 收藏和浏览历史支持菜谱、食材、水果、饮品、调料统一内容类型。
- [ ] 菜谱步骤明确支持图片、视频、视频时长、计时、顺序和文案。
- [ ] 菜谱可见范围使用枚举并由服务端强制：仅自己、共享家庭。
- [ ] 饮品拆分基础饮品与可调制饮品，调制型支持用料、基酒、器具、步骤和计时。
- [ ] 将 `relatedRecipes` 等长期 JSON 关系迁移为显式关联表。
- [ ] 文件模型补充上传人、来源端、尺寸、时长、哈希、状态和引用信息。

### 1.3 数据迁移原则

- [ ] 所有 migration 只增量执行，不清空生产数据。
- [ ] 先增加新字段/新表，再双写和回填，最后切读，确认稳定后才移除旧字段。
- [ ] 每个回填脚本支持重复执行并输出成功/跳过/失败数量。
- [ ] 任何枚举迁移都必须提供旧值映射和未知值兜底。

### 验收门槛

- 越权测试：A 用户不能读取/修改 B 用户资产或非成员家庭数据。
- 数据库迁移、回填、回滚演练通过。
- Prisma 校验、后端构建和鉴权单元测试通过。

## 阶段 2：统一文件与媒体服务

**目标：** 后台和 C 端上传的图片、头像与视频真实持久化并可安全使用。

### 工作内容

- [ ] 建立统一 `/api/files` 上传、查询和删除协议，后台与 C 端复用同一服务。
- [ ] 开发环境可使用本地存储；生产环境使用对象存储 + CDN，URL 不依赖单机磁盘。
- [ ] 图片支持 JPG/PNG/WebP，头像要求至少 512×512 正方形，单张不超过 5MB。
- [ ] 菜谱/步骤视频支持明确的 MP4/MOV/WebM 白名单和大小/时长限制；发布前以目标市场兼容性为准最终确定。
- [ ] 上传后提取尺寸、时长、MIME、哈希，服务端二次校验，不信任扩展名。
- [ ] 支持多图排序、单张删除、替换封面、上传失败重试和进度展示。
- [ ] 删除文件前检查引用；未引用临时文件按计划清理。
- [ ] 头像、家庭头像、菜谱封面、多图、步骤图/视频全部改用真实文件 ID。

### 验收门槛

- 后台上传的资源可在 C 端正常显示。
- C 端上传后重装 App 或换设备仍可读取。
- 非法类型、超限文件、上传中断、重复文件有明确反馈。
- 删除仍被内容引用的文件会被阻止。

## 阶段 3：后台真实配置能力

**目标：** 让公共内容和首页真正由后台配置，不再依赖前端硬编码。

### 3.1 首页运营

- [ ] 顶部频道 CRUD、排序、启停和默认频道。
- [ ] 每个频道独立 Banner 轮播、跳转目标、有效期、排序和上下架。
- [ ] 首页模块新增/编辑/排序/启停，支持手动选择内容和规则内容源。
- [ ] 模块配置只允许选择设计系统预置的模块类型，不允许自由输入 CSS。
- [ ] 发布前预览使用与 C 端同一 API DTO，不能使用后台本地 mock 预览。
- [ ] 增加配置版本、发布、回滚和操作日志。

### 3.2 内容管理

- [ ] 菜谱表单覆盖封面、多媒体、基础信息、用料、图文/视频步骤、计时、小贴士、分类、标签、相关推荐和发布状态。
- [ ] 食材/水果表单覆盖时令、参考价/斤、单位、挑选、保存、吃法、禁忌、相关菜谱。
- [ ] 调料表单覆盖风味、建议用量、替代品、保存方式、相关菜谱。
- [ ] 饮品表单根据类型动态显示：基础资料，或基酒/辅料/器具/调制步骤/计时。
- [ ] 分类、标签、单位使用统一真实 API，移除 localStorage/mock 字典。
- [ ] 所有列表具备搜索、筛选、分页、上架/下架、批量操作和失败反馈。

### 3.3 MVP 后台范围控制

以下占位页面首发前不强行建设，无法真实工作的菜单应隐藏或标记“暂未开放”，不能以 mock 冒充功能：

- 复杂经营报表、AI 运营、价格预测、评论/晒菜审核、付费能力。
- 与 C 端首发流程无关的 API 配置中心高级功能。
- 无真实数据源的采购趋势、告警、来源分析。

### 验收门槛

- 后台新建一条内容，发布后可经数据库/API 在 C 端展示。
- 修改顺序、上下架、图片、文案后 C 端刷新可同步。
- 下架内容不可通过列表、搜索或直接详情 ID 继续访问。
- 后台页面不再展示会保存到 localStorage 的伪配置。

## 阶段 4：API 契约与服务层收敛

**目标：** 建立稳定的 App API v1，使正式 C 端只依赖服务层，不直接拼装后端字段。

### 工作内容

- [ ] 将过大的 `mobile.ts` 按 auth、profile、family、basket、content、favorite、history、notification、upload 拆分。
- [ ] 统一成功、分页、验证失败、未登录、无权限、不存在和业务冲突响应格式。
- [ ] 为首页频道、Banner、模块、列表卡片和五类详情定义正式 DTO。
- [ ] 为菜谱烹饪与饮品制作定义统一 GuidedFlow DTO：步骤、媒体、文案、计时、小贴士、进度。
- [ ] 为搜索、收藏、浏览、菜篮、家庭偏好、通知定义 DTO 和幂等策略。
- [ ] 收藏、加入菜篮、完成采购、发送开饭提醒等写操作增加重复点击保护。
- [ ] 使用运行时 Schema 校验后台输入与 API 输出，避免数据库字段直接泄露到 C 端。
- [ ] 为 C 端保留兼容期，但明确旧字段下线版本和日期。

### 核心接口验收链路

1. 后台发布菜谱。
2. 首页模块返回该菜谱卡片。
3. 菜谱详情返回用料、步骤、小贴士、家庭提醒。
4. 加入菜篮将用料合并进当前家庭。
5. 去烹饪返回逐步制作数据并支持计时。
6. 收藏/取消收藏和浏览记录同步到“我的”。

### 验收门槛

- OpenAPI 或等价契约文档与实现一致。
- 契约测试覆盖上述纵向链路及错误状态。
- 服务端不再依赖客户端传入的当前用户 ID。

## 阶段 7：自动测试与质量验收

**目标：** 覆盖正向、逆向、权限、网络和设备适配，不靠人工点几下判断可发布。

### 7.1 自动测试层级

| 层级 | 重点 |
|---|---|
| 单元测试 | Token、权限、价格/单位、内容映射、推荐规则、食材合并 |
| 数据库测试 | migration、回填、唯一约束、软删除、事务和并发 |
| API 集成 | 后台发布到 App 读取、鉴权、上传、收藏、菜篮、家庭 |
| 契约测试 | Admin DTO、App DTO、前端 TypeScript 类型一致 |
| 后台 E2E | 新增→编辑→发布→C 端可见→下架→不可见 |
| C 端 E2E | 首页→详情→收藏/菜篮→制作；家庭创建/加入；我的资产 |
| 真机测试 | 相册、相机、扫码、视频、计时、推送、安全区、弱网 |

### 7.2 必测正向流程

- [ ] 新用户注册登录 → 完善资料 → 创建/扫码加入家庭。
- [ ] 后台发布菜谱 → 首页可见 → 详情 → 加菜篮 → 去烹饪 → 完成。
- [ ] 后台发布食材 → 分类/详情 → 挑选弹层 → 相关菜谱。
- [ ] 可调制饮品 → 查看用料 → 加菜篮 → 去制作 → 完成。
- [ ] 添加个人菜谱 → 仅自己/共享家庭 → 修改后各范围显示正确。
- [ ] 家庭成员设置忌口 → 采购和烹饪前出现正确提醒。
- [ ] 家庭管理员发送开饭提醒 → 所有目标成员收到通知。

### 7.3 必测逆向流程

- [ ] Token 过期、用户禁用、家庭权限不足、被移出家庭。
- [ ] 重复加入菜篮、重复收藏、重复发送提醒和连续提交。
- [ ] 后台下架内容后，收藏/历史/直达详情的处理。
- [ ] 图片或视频上传超限、类型伪造、断网、中断、失败重试。
- [ ] 空家庭、空菜篮、空收藏、无搜索结果、CMS 空模块。
- [ ] 后端超时、500、对象存储失败、数据库短暂不可用。
- [ ] 200% 字体、窄屏、长标题、长单位、多成员偏好。

### 7.4 性能指标建议

- 首屏 API 和图片分离加载，避免一个失败导致整页白屏。
- 非首屏图片懒加载并声明尺寸，避免布局跳动。
- 首页模块分页/游标加载，不一次返回全部内容。
- 服务端为高频列表、家庭菜篮和内容状态建立必要索引。
- 以真实设备测量启动、首屏、列表滚动、图片内存和视频播放；指标基线在阶段 0 记录，发布门槛以基线改善和无明显卡顿为准。

### 验收门槛

- 三端构建、类型检查、单元/集成/E2E 全通过。
- P0/P1 缺陷清零，P2 有明确延期记录和规避方案。
- 核心流程在至少一台低性能 Android 和一台当前 iPhone 真机通过。

## 6. 推荐的并行工作流

在阶段 0 和阶段 1 契约确认后，可并行使用多个智能体/开发工作流，但共享 Schema 和 DTO 必须由一个负责人合并：

| 工作流 | 负责范围 | 可并行阶段 | 依赖 |
|---|---|---|---|
| A 数据与 API | Prisma、鉴权、上传、内容/家庭服务、契约测试 | 1–4 | 先冻结 DTO |
| B 后台配置 | 首页运营、内容表单、字典、发布/回滚 | 2–3 | API/Schema |
| C C 端基础 | 设计系统、AppShell、请求/状态、公共组件 | 4–5 | DTO 稳定 |
| D C 端业务 | 首页分类、详情制作、家庭菜篮、我的 | 5 | 公共组件/接口 |
| E 数据运营 | 导入模板、内容清洗、首发编排 | 3、6 | 后台可用 |
| F QA 与发布 | 契约/E2E/真机、CI、部署、合规、商店 | 0、7–9 | 全程参与 |

### 并行纪律

- 不允许多个工作流同时修改同一 Prisma 模型或同一 DTO 文件。
- 每个工作流使用独立分支/工作区，合并前通过各自验证。
- 任何字段变更先更新契约，再更新后端、后台和 C 端。
- UI 智能体不得重画已确认顶部框架、Banner、主图和底部导航。

## 7. 推荐执行顺序与里程碑

| 里程碑 | 完成定义 |
|---|---|
| M0 基线冻结 | 页面/接口/表/后台追踪矩阵完成，原型只读 |
| M1 数据安全 | 用户接口全部 JWT 化，偏好/上传/采购/通知模型可用 |
| M2 运营闭环 | 后台发布的菜谱和首页模块可在旧 C 端接口层真实读取 |
| M3 纵向切片 | 新首页→菜谱详情→菜篮→去烹饪全流程通过 |
| M4 页面替换 | 正式 C 端全部 P0 页面按原型完成且无长期 mock |
| M5 家庭闭环 | 创建/加入/成员权限/偏好/菜篮/提醒可用 |
| M6 候选版本 | 自动测试、真机、性能、安全和内容验收通过 |
| M7 灰度发布 | staging、签名、隐私、商店材料和内测完成 |
| M8 正式发布 | 灰度指标稳定、全量发布、监控和回滚就绪 |

不建议直接从当前状态跳到“替换整个 C 端”。必须先完成 M1 和 M2，否则只是把原型中的假数据换到另一套漂亮页面里。

## 8. 首发范围与明确不做

### 首发必须有

- 后台配置驱动首页、频道和五类内容。
- 菜谱/食材/水果/饮品/调料列表与详情。
- 菜谱烹饪与可调制饮品制作。
- 登录注册、个人资料、头像、收藏、浏览、我的菜谱和添加菜谱。
- 家庭创建/扫码加入、成员与权限、偏好共享、家庭菜篮和采购记录。
- 系统/家庭提醒、上传、隐私、账号注销。
- 加载、空、错误、离线、重试和发布运维能力。

### 首发不做

- 社交聊天、关注、公开评论和晒菜社区。
- AI 自动生成菜谱或识图识菜。
- 家庭库存、“家里已有”、独立买菜模式。
- 支付、会员、广告和复杂商业化。
- 复杂经营报表、价格预测和无真实数据源的运营大屏。
- 主页壁纸、草稿入口和大量个性化皮肤。

## 9. 最终发布完成标准

只有同时满足以下条件，才可称为“可以发布使用的 App”：

- [ ] 公共内容由后台配置、数据库落库、API 返回，C 端无长期硬编码业务数据。
- [ ] 用户资产和家庭数据由 JWT 与成员权限保护，无客户端 `userId` 越权入口。
- [ ] 所有正式路由均有真实页面或明确隐藏，不存在 mock 冒充功能。
- [ ] 图片、视频、头像、步骤媒体使用统一上传和生产对象存储。
- [ ] 首页、分类、详情、制作、家庭、菜篮、我的及二级页面核心流程闭环。
- [ ] 正向、逆向、权限、弱网、空态、错误态和重复点击测试通过。
- [ ] 360–430px、100%–200% 字体和 iOS/Android 真机适配通过。
- [ ] staging/prod、备份、监控、日志、告警、CI/CD 和回滚可用。
- [ ] 隐私政策、数据披露、账号注销、权限说明和商店材料完成。
- [ ] 内测和灰度指标稳定，无 P0/P1 缺陷。

## 11. 主要风险与控制方式

| 风险 | 控制方式 |
|---|---|
| 原型反复变化导致正式代码返工 | 原型冻结，变更走产品决策和契约更新 |
| 大爆炸替换造成旧功能全部失效 | 路由逐页替换、纵向切片、功能开关和回滚 |
| 后台配置破坏 UI | 后台只选择预置模块，不配置视觉 Token |
| Schema 被多人同时修改 | 单一 Schema/DTO 负责人，先契约后并行 |
| 旧数据无法迁移 | 增量表、双写、幂等回填、迁移前备份 |
| 用户隐私或家庭数据越权 | JWT 全迁移、家庭角色测试、操作审计 |
| 上传占满服务器或产生破图 | 对象存储、限制、元数据校验、临时文件清理 |
| 应用市场因隐私/注销被拒 | 发布前数据清单、App 内及网页删除入口、审核账号 |
| 旧 App 与新 API 不兼容 | API v1 兼容窗口、灰度、后端向后兼容 |
| 内容版权和质量问题 | 来源记录、发布审核、紧急下架与回滚 |
