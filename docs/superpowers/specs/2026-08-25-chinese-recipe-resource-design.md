# 中国菜谱资源接入与治理设计

## 1. 背景

当前后台已经具备 Provider 配置、连接测试、同步到导入池、数据校验、人工修正、确认导入和审核发布能力，但菜谱资源中混入了较多国外西餐和英文内容，不符合“家里有菜”面向中国家庭时令饮食的产品定位。

截至 2026-08-25 的只读审计显示：正式库有 18 道菜谱，其中 7 道标题不含中文、6 道缺少封面；导入池仍有约 150 条待处理菜谱。现有 TheMealDB 数据以海外菜谱为主，应退出中国菜谱主链路。现有 Proj.Kitchen 和 TianAPI 已具备中文菜谱接入配置，可作为候选主源，但正式启用前仍需确认服务稳定性、额度和内容使用许可。

本设计只处理菜谱资源，不同时改造食材、水果、调料和酒水。后四类资源在菜谱链路稳定后分别设计和实施。

## 2. 目标

1. 后台菜谱资源默认只接入适合中国家庭烹饪的中文菜谱。
2. 国外西餐和纯英文菜谱不再进入新的待导入队列。
3. 所有外部菜谱必须经过原始记录、标准化、质量校验、人工审核和发布流程。
4. 现有国外菜谱和测试菜谱可追踪、可隐藏，不直接物理删除。
5. 首批形成 100 至 150 道可在 C 端真实展示的高质量中国家常菜。
6. 同一来源重复同步时保持幂等，不重复创建正式菜谱。

## 3. 非目标

- 不建设爬虫平台。
- 不抓取未明确允许复用的网页内容。
- 不自动生成或自动发布 AI 菜谱。
- 不在本阶段处理食材营养、水果、调料和酒水数据。
- 不清空数据库，不删除历史导入批次和原始响应。
- 不让 C 端直接请求第三方菜谱 API。

## 4. 方案选择

### 方案 A：修复现有导入链路并建立中国菜谱准入规则（采用）

保留现有 `ResourceApiProvider`、`ResourceImportBatch`、`ResourceImportItem`、`Recipe`、`RecipeStep` 和 `RecipeIngredient` 模型，在同步和确认导入前增加中国菜谱过滤、质量校验、来源治理与后台批量处理能力。

优点是复用当前架构、风险低、能保留原始数据和历史记录。缺点是需要先治理现有待处理数据。

### 方案 B：清空菜谱后重新导入

实现直观，但会破坏已有内容、关联关系和测试记录，不符合项目的非破坏性原则，不采用。

### 方案 C：C 端实时查询第三方 API

会受到第三方稳定性、限流、许可和响应速度影响，也绕过后台审核发布，不采用。

## 5. 数据源策略

### 5.1 主源

首选现有中文菜谱 Provider：

- `proj_kitchen`：候选主源，用于批量获取中文菜谱列表和详情。
- `tianapi_caipu`：候选补充源，按关键词获取中国菜谱，依赖服务端 API Key。

两者在生产同步前必须记录：来源主页、使用许可或授权说明、调用额度、请求参数、最近测试时间和最近错误。

### 5.2 停止作为主源

- `themealdb_recipe`：停用新的菜谱同步，保留 Provider、历史批次和原始数据供追溯。
- `mock_recipe`：保持禁用，仅保留历史测试记录。

停用采用状态变更，不物理删除 Provider。

### 5.3 来源白名单

菜谱同步接口只允许状态为 `ACTIVE` 且通过菜谱来源白名单的 Provider 创建新批次。后台页面的禁用只是交互提示，后端必须再次强制校验。

## 6. 中国菜谱准入规则

菜谱进入待审核池前必须满足以下条件：

1. 标题包含中文，去除测试前缀和无意义编号后长度为 2 至 40 个字符。
2. 至少包含 2 个有效用料。
3. 至少包含 1 个有效制作步骤。
4. 分类属于允许的中国菜谱分类；外部分类必须经过映射，不能直接创建 `Chicken` 等英文分类。
5. 不属于饮品、鸡尾酒或纯包装食品。
6. 来源外部 ID 或来源 URL 至少存在一个。
7. 同一 `provider + externalId` 不得重复；无外部 ID 时使用规范化标题和分类辅助去重。
8. 图片 URL 必须合法；缺少图片可以进入导入池，但不能直接发布。

建议的首批分类白名单：

- 家常菜
- 快手菜
- 素菜
- 荤菜
- 汤羹
- 凉菜
- 主食
- 早餐
- 烘焙
- 地方菜
- 节气时令

分类映射必须显式维护。例如 `素食`、`蔬菜类` 可映射到 `素菜`；无法识别的外部分类标记为“待分类”，不得自动创建新分类。

## 7. 数据流

```text
中文菜谱 Provider
  → 拉取原始响应并保存 RawImportRecord
  → 创建 ResourceImportBatch
  → 标准化为 ResourceImportItem
  → 中国菜谱准入过滤
  → 分类映射、中文清洗、用料和步骤校验
  → 去重与质量评分
  → 后台资源接入中心人工修正
  → 确认导入 Recipe / RecipeStep / RecipeIngredient
  → auditStatus = PENDING，isPublish = false
  → 审核中心通过
  → 内容管理发布
  → C 端展示
```

同步不得直接发布正式内容。确认导入、审核通过、发布是三个独立动作。

## 8. 字段映射

### 8.1 Recipe

| 标准字段 | 来源字段示例 | 规则 |
|---|---|---|
| `title` | `name`、`title`、`cpName`、`menu` | 必须中文化并去除测试前缀 |
| `subtitle` | `subtitle`、摘要 | 可空 |
| `description` | `description`、`intro`、`imtro` | 去除 HTML 和来源广告 |
| `cover` | `cover`、`pic`、`image`、`albums[0]` | 发布前转存为受管文件 |
| `categoryId` | 外部分类 | 通过分类映射表解析 |
| `cookTime` | `cookTime`、`time` | 统一为分钟 |
| `servings` | `servings` | 统一为人数 |
| `difficulty` | `difficulty`、`grade` | 映射为简单、普通、进阶 |
| `sourceName` | Provider 名称 | 必填 |
| `sourceRecipeId` | 外部 ID | 优先作为幂等键 |
| `sourceUrl` | 原始详情地址 | 可追溯 |

### 8.2 RecipeIngredient

- 保留原始名称、用量和单位。
- 对名称做别名标准化，例如“西红柿”与“番茄”映射到统一食材。
- 匹配到正式食材时写入 `ingredientId`；未匹配时保留文字名称并进入待关联清单。
- 不因食材暂未建档而阻止菜谱进入人工审核。

### 8.3 RecipeStep

- 保留原始步骤顺序。
- 删除空步骤和重复步骤。
- 步骤描述必须为中文且可执行。
- 步骤图片和视频沿用现有受管媒体规则。

## 9. 质量评分与状态

每条导入项计算 100 分质量分：

| 项目 | 分值 |
|---|---:|
| 中文标题有效 | 20 |
| 分类映射成功 | 15 |
| 用料完整 | 20 |
| 步骤完整 | 20 |
| 封面可用 | 15 |
| 来源可追溯且通过去重 | 10 |

- 低于 60 分：`FAILED`，显示明确失败原因。
- 60 至 79 分：保留在导入池，需要人工补齐。
- 80 分及以上：允许提交确认导入。
- 正式表仍保持 `auditStatus = PENDING`、`isPublish = false`，直到审核和发布完成。

现有状态模型若暂不增加新枚举，可继续使用 `PENDING` 表示需要人工处理，并通过 `filterCode` 和质量分区分原因。

## 10. 现有数据治理

### 10.1 正式菜谱

对现有 18 条菜谱执行只读盘点后分组处理：

- 中文且字段完整：保留并复核分类、图片和来源。
- 英文或国外西餐：设置为未发布；如确有业务价值，可保留在后台但不进入中国菜谱默认内容池。
- E2E、测试名称或无意义标题：设置为未发布并标记测试数据，不直接物理删除。
- 缺封面、缺步骤：退回待完善状态。

### 10.2 导入池

- `themealdb_recipe` 的待处理项批量标记为忽略，不导入正式库。
- `proj_kitchen` 和 `tianapi_caipu` 的待处理项重新执行中国菜谱准入规则。
- 重复项保留失败记录和重复目标 ID，避免再次同步。
- 已导入但正式目标不存在的历史孤儿记录进入异常清单，不自动重建。

所有批量状态变更必须可统计、可记录操作人，并避免影响其他资源类型。

## 11. 后台调整

### API 接口管理

- 为菜谱 Provider 显示“中国菜谱主源 / 补充源 / 已停用海外源”标识。
- 已禁用 Provider 不显示同步按钮。
- 展示许可说明、额度、最近同步、最近错误和导入批次数。

### 资源接入中心

- 菜谱列表增加：来源、是否中文、质量分、分类映射、缺失字段和重复状态筛选。
- 支持批量忽略海外菜谱。
- 支持批量提交 80 分以上的中国菜谱。
- 编辑抽屉中同时展示原始数据与标准化数据。

### 内容管理

- 菜谱列表增加来源和质量提示。
- 测试数据、海外菜谱默认不发布。
- 批量发布前再次校验审核状态和核心字段。

## 12. 接口约束

需要调整或补充的管理接口行为：

- `POST /api/admin/resource-api-providers/:id/sync`
  - 拒绝已禁用或不在菜谱白名单中的 Provider。
  - 对菜谱执行中文准入、分类映射和质量评分。
- `GET /api/admin/resource-imports/items`
  - 支持按 Provider、中文状态、质量区间、缺失字段和 `filterCode` 筛选。
- `POST /api/admin/resource-imports/confirm`
  - 只允许确认校验通过且质量达标的中国菜谱。
- 批量忽略接口
  - 仅修改导入项状态，不删除原始数据。

所有接口继续使用项目统一响应结构和后台 RBAC。

## 13. 错误处理

- 第三方超时、HTTP 429、服务错误：批次失败，保存错误摘要，不创建空导入项。
- API Key 缺失：Provider 保持禁用并明确提示缺失环境变量。
- 外部字段变化：原始响应仍保留，标准化失败项写入 `filterCode`。
- 单条数据失败：不阻断同批次其他数据进入导入池。
- 分类无法映射：进入待分类，不自动扩张分类树。
- 重复数据：保留重复目标 ID，禁止再次确认导入。

## 14. 验收标准

1. TheMealDB 和 Mock 菜谱不能再创建新的待导入菜谱。
2. Proj.Kitchen 或 TianAPI 能完成测试、同步、预览、人工修正和确认导入。
3. 纯英文标题、海外分类、无步骤或无用料的记录无法确认导入。
4. 同一来源同一外部 ID 重复同步不会创建第二道正式菜谱。
5. 导入后的菜谱默认未发布且待审核。
6. 审核通过并发布后，C 端能通过真实接口展示。
7. 现有海外菜谱和测试菜谱被隐藏但未物理删除。
8. 首批至少 100 道中国菜谱达到发布标准，且不存在纯英文分类。

## 15. 测试策略

- 单元测试：中国标题识别、分类映射、用料和步骤校验、质量评分、去重键生成。
- 路由测试：禁用 Provider 拦截、白名单校验、批量忽略、确认导入门槛。
- 数据库测试：导入事务、默认审核和发布状态、来源字段、重复导入。
- 后台测试：筛选、预览、编辑、批量忽略、批量确认、错误提示。
- 联调测试：Provider → 导入池 → 正式表 → 审核 → 发布 → C 端详情完整闭环。

## 16. 实施边界

实施只修改本需求必要的 `server/`、`admin-frontend/` 和相关测试/文档，不修改历史 `admin-backend/`、`backend/`，不清空数据库，不把第三方 Key 写入代码或日志。
