# 菜谱用料真实食材关联与透明图展示设计

## 目标

菜谱详情页的每条用料都应来自后台食材资源库，并在 C 端展示对应食材的透明实物图。用料卡片采用横向滚动布局，图片区域透明、无卡片底色；点击后进入对应的食材、水果或调料详情页。

本次改造同时解决四个现状问题：

- `RecipeIngredient.ingredientId` 允许为空，后台目前只要求填写名称。
- 后台修改已选名称时不会清除旧 `ingredientId`，可能形成名称与关联对象不一致的脏数据。
- C 端会按用料名称再次搜索食材图片，造成“看起来有关联，实际未绑定”。
- 现有 98 条有效菜谱用料中只有 1 条已关联食材；97 条未关联，且只有 10 个唯一名称可与现有食材库精确匹配。

## 采用方案

采用“数据库兼容旧数据、业务发布强校验、存量渐进修复”的方案。

`RecipeIngredient.ingredientId` 暂时保留可空，避免直接迁移破坏现有菜谱。草稿允许暂存未绑定用料，但菜谱提交审核、审核通过或发布时，每条有效用料必须：

1. 绑定一个未删除且启用的 `Ingredient`。
2. 绑定对象的名称与展示类型来自关联记录，不信任自由文本伪造关联。
3. 绑定对象配置可用的 `transparentImage`。

不满足条件时拒绝发布并返回可定位到具体用料的中文错误。已经发布的历史菜谱不自动批量下架，先在后台标记为待补绑；当它再次编辑或发布时执行新规则。

不采用以下方案：

- 直接把数据库字段改为非空：97 条存量记录会阻塞迁移，也无法解决透明图缺失。
- 按名称自动创建食材：会把测试值、英文词和同义词直接污染正式资源库。
- C 端继续按名称搜索图片：无法保证搜索结果就是菜谱实际绑定的食材。

## 数据模型与数据职责

现有关系继续作为唯一真实来源：

```text
Recipe
  └─ RecipeIngredient
       ├─ ingredientId → Ingredient.id
       ├─ name（兼容快照，不作为关联依据）
       ├─ amount / unit / note（菜谱自己的用量信息）
       └─ sortIndex

Ingredient
  ├─ name（C 端显示名称）
  ├─ transparentImage（紧凑用料卡片唯一图片来源）
  ├─ category.type（决定详情页类型）
  └─ bizId / code（对外稳定标识）
```

本次不强制修改 Prisma 字段的可空性。关联完整性由菜谱发布校验服务保证，数据库外键继续防止无效 ID。

## 后台编辑行为

菜谱的“食材配料”和“调料配比”统一使用资源库选择器：

- 输入关键词只用于搜索，不代表已经绑定。
- 选择搜索结果后写入 `ingredientId`，名称显示为资源库规范名称。
- 用户再次修改名称文本时立即清空 `ingredientId`，避免旧关联残留。
- 每行显示关联状态和透明图缩略预览。
- 已绑定且有透明图显示“已关联”；未绑定显示“请选择资源库食材”；缺透明图显示“食材缺少透明图”。
- 保存草稿允许存在待补绑行；提交审核、审核通过和发布时必须全部合格。

食材与调料仍共用 `Ingredient` 资源模型，通过分类类型区分，不为菜谱用料另建重复资源表。

## 后端接口与校验

### 管理端菜谱接口

管理端菜谱详情返回每条用料的关联摘要，至少包含：

- 对外食材 ID。
- 名称。
- `transparentImage`。
- 分类类型。
- 关联状态。

创建和更新草稿可以接受空 `ingredientId`。当请求试图将菜谱设为发布状态或审核通过状态时，后端执行统一发布质量校验，不能只依赖前端按钮校验。

错误响应保持现有统一结构，例如：

```json
{
  "code": 422,
  "message": "菜谱用料未满足发布要求：盐未关联食材；番茄缺少透明实物图",
  "data": null
}
```

### C 端菜谱详情接口

C 端接口直接返回已经序列化的关联食材：

```json
{
  "ingredientId": "ingredient_xxx",
  "name": "黄瓜",
  "amount": "1根",
  "ingredient": {
    "id": "ingredient_xxx",
    "name": "黄瓜",
    "transparentImage": "/uploads/ingredients/cucumber.webp",
    "categoryType": "INGREDIENT"
  }
}
```

C 端不再调用食材列表接口按名称补图，也不再使用普通封面冒充透明图。历史未关联或图片失效时保留文字占位，页面不能白屏。

## C 端展示

用料区参考用户提供的效果图，但沿用项目全局色彩、字体和间距 token：

- 使用横向滚动列表，不压缩成固定四列网格。
- 每项为等宽紧凑卡片，图片在上、名称与用量在下。
- 透明 PNG/WebP 使用 `aspectFit`，图片容器和卡片均为透明背景，不增加米色、白色或其他底色。
- 不裁切实物图，不给透明图加圆形遮罩或缩略图边框。
- 名称使用关联食材的规范名称；用量继续使用菜谱自己的 `amount + unit`，并支持份数换算。
- 有真实关联时整卡可点击，根据 `categoryType` 进入食材、水果或调料详情。
- 未关联或无透明图的历史数据显示统一文字占位；未关联项不可伪装成可点击食材。
- 图片加载失败时切换文字占位，并保留名称和用量。

## 存量修复

提供可重复执行的安全修复流程，不做模糊自动建档：

1. 对未关联用料进行去空格、大小写统一后的精确名称匹配。
2. 只有唯一命中现有有效食材时才自动补写 `ingredientId`。
3. 无命中、多命中、测试值和英文旧数据进入待人工处理清单。
4. 缺透明图的食材在资源库补图后，所有关联菜谱自动获得正确展示，不向菜谱记录复制图片 URL。
5. 修复脚本默认 dry-run，明确传入执行参数才写库，并输出关联、跳过和缺图数量。

## 错误与兼容处理

- 草稿中未绑定用料：允许保存，后台明确提示，禁止发布。
- 关联食材已删除或停用：视为无效关联，禁止发布。
- 关联食材缺透明图：禁止发布，并引导到食材管理补图。
- C 端收到历史未关联数据：显示文字占位，不发起按名称搜索。
- 透明图请求失败：降级为文字占位，不回退普通封面，保持“无底色透明实物图”的视觉约束。
- 同名食材：后台必须由管理员选择具体记录；修复脚本不自动处理多命中。

## 测试与验收

实施阶段按 TDD 进行，先增加失败测试，再写最小实现。

### 后端

- 草稿可保存未绑定用料。
- 发布菜谱时，未绑定、关联对象无效或缺透明图均返回 422。
- 合格关联可以发布。
- C 端详情返回对外食材 ID、规范名称、透明图和分类类型。
- 存量修复 dry-run 不写库；仅唯一精确匹配可执行补绑。

### 后台

- 手工修改名称会清空旧 `ingredientId`。
- 从搜索结果选择后写入真实关联并展示透明图与状态。
- 发布前能定位未绑定或缺图的具体行。
- 后端拒绝时展示原始中文错误，不出现假成功。

### C 端

- 不再按名称调用 `listIngredients` 补图。
- 只显示关联食材的 `transparentImage`，不回退普通封面。
- 卡片与图片容器背景透明，横向滚动正常。
- 点击三种分类分别进入正确详情页。
- 无图与图片加载失败均显示文字占位。
- 加载、空态、错误态和份数换算保持正常。

### 联调验收

1. 在食材管理为“黄瓜”上传透明 WebP。
2. 在菜谱后台选择“黄瓜”，填写用量并发布。
3. 打开 C 端菜谱详情，确认显示无底色透明黄瓜图、规范名称和用量。
4. 点击黄瓜卡片，确认进入黄瓜详情。
5. 删除关联或清空透明图后再次发布，确认后端阻止并给出明确原因。

## 影响范围与风险

影响 `server/`、`admin-frontend/` 和 `frontend/` 的菜谱用料链路，不修改历史后端目录。

主要风险是存量数据质量较低：97 条未关联用料中只有少量可以安全自动匹配，且透明图覆盖不足。因此发布强校验必须与后台待修复提示、dry-run 修复工具一起交付，不能直接把数据库字段改为非空或批量自动建食材。
