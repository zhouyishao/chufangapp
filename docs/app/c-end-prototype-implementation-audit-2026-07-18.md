# C 端原型与正式项目差距审计

日期：2026-07-18  
范围：`docs/prototypes/home-feed-interactive/` 对照 `frontend/`、`server/` 与相关后台配置页。  
目的：在正式 UI/UX 重构前，明确哪些能力保留、重构、新增、退役，以及哪些页面依赖后端先补齐。

## 1. 审计结论

当前正式 C 端不是空项目：已存在 37 个路由、统一请求层、首页 CMS 模块、菜谱/食材详情、家庭、菜篮、收藏、浏览历史和创建菜谱等基础链路。因此不应整套推翻重写。

但原型与正式实现仍有三类明显差距：

1. **视觉结构差距**：正式首页、分类、菜篮、我的及详情页仍保留多套旧结构；水果、调料、饮品详情尤其接近通用信息卡，与已确认原型不一致。
2. **交互闭环差距**：通知、聚餐提醒、隐私与家庭共享、饮品逐步制作等原型流程没有独立正式页面；部分设置只停留在本地开关或 Toast。
3. **数据边界差距**：家庭菜篮当前按 `userId + familyId` 查询，不能让同一家庭所有成员看到同一份菜篮；家庭口味只有家庭级聚合记录，无法表达“谁喜欢/忌口/过敏什么”；头像与个人资料仍主要存本地。

建议采用“**保留数据层和已通链路，重构页面层，优先修复家庭共享与鉴权边界**”的方式推进。

## 2. 审计基线

### 2.1 原型意图

原型已覆盖：

- 首页推荐流与菜谱、食材、水果、饮品频道。
- 分类页五大类：菜谱、食材、水果、饮品、调料。
- 菜谱、食材、水果、饮品、调料详情。
- 菜谱去烹饪与鸡尾酒/调制饮品去制作。
- 家庭菜篮、家庭切换、食材/菜谱视图、食材挑选底部面板、家庭口味提醒。
- 我的、我的菜谱、添加菜谱、收藏、最近浏览、个人资料、家庭管理、邀请/扫码加入。
- 通知、家庭聚餐提醒、账号设置等补充流程。

### 2.2 正式实现证据

- 路由已集中登记在 `frontend/src/pages.json`，核心页面大多已有文件。
- 请求和 DTO 主要集中在 `frontend/src/services/public-api.ts`。
- 首页已接入顶部频道、频道 Banner、频道内容和 CMS 模块接口。
- 后端已有 Recipe、Ingredient、Beverage、Family、FamilyMember、Favorite、ViewHistory、PurchaseListItem 等模型。
- 后台已有菜谱、食材、饮品、首页频道、Banner 和内容模块配置能力。

### D. 建议退役或合并

以下项目先标记为候选，不在本轮直接删除；确认无正式入口和数据依赖后再移除。

| 候选 | 建议 |
|---|---|
| 我的页面“主页背景/壁纸”编辑 | 用户已明确取消，移除 UI、临时图片状态与相关样式 |
| `pages/category-filter` 与 `pages/ingredients` 双分类实现 | 合并为一个正式分类容器，避免两套筛选/模块解析 |
| `pages/today`、`pages/serving-recommendation`、`pages/family-menu` | 若最终信息架构无独立入口，能力并入推荐流/菜篮，不保留孤岛页 |
| 页面内重复 topbar/state-card/glass-card 样式 | 合并为全局组件；普通内容卡停止使用毛玻璃 |
| `services/profile.ts` 的本地假默认资料 | 接真实 profile 后仅保留无用户时的匿名占位，不再作为数据源 |
| 本地账号密码存储 | 真实鉴权上线后必须移除，不能和服务端会话并存 |
| 饮品详情解析 `description` JSON 的兼容逻辑 | 结构化字段 API 上线后仅短期兼容旧数据，随后迁移并删除 |
| Prototype 中的硬编码演示内容 | 只保留为设计验收基线，不复制进正式业务代码 |

### E. 后端、数据库和后台依赖

### E1. P0：不先修就会造成正式页面返工

1. **家庭菜篮共享语义**  
   当前 `/mobile/basket-items` 使用 `userId` 和可选 `familyId` 同时过滤；成员 A 添加的家庭条目，成员 B 无法查询。应改为：个人菜篮按 `userId`，家庭菜篮按 `familyId + 家庭成员鉴权`；条目保留 `createdByUserId` 用于审计，但不作为家庭读取条件。

2. **真实 C 端鉴权**  
   当前登录接口按手机号直接 upsert 用户，其他接口大量信任客户端传入 `userId`。需要 JWT/会话中间件，从服务端身份取得用户 ID；收藏删除、浏览历史、家庭、菜篮都必须校验资源归属。

3. **个人偏好而非单一家庭偏好**  
   当前 `FamilyPreference` 是一个家庭一条聚合记录，无法回答“谁不吃香菜、谁花生过敏、谁喜欢清淡”。建议新增 `UserPreference` 或 `FamilyMemberPreference`，字段包含喜欢、忌口、过敏和共享开关；家庭页只聚合展示已共享信息。

4. **上传与资料更新**  
   数据库已有 User.avatar 和 Family.avatar，但缺少完整的 C 端上传、资料更新和家庭头像更新 API。需要统一文件上传返回 URL，并限制图片/视频格式、大小和数量。

5. **饮品结构化返回**  
   Beverage 模型已有 `drinkType`、`cocktailMethod`、`baseSpirit`、`ingredients`、`measures`、`garnish`、`instructions` 等字段，但 C 端 DTO 只返回基础字段。API 和后台表单需统一字段，支持制作步骤与“去制作”。

### E2. P1：完成内容闭环所需

- 新增 Notification、FamilyEvent/GatheringReminder、NotificationReceipt 数据结构和接口。
- 新增 PurchaseBatch/PurchaseBatchItem，采购完成后冻结本次快照，采购记录不再从当前菜篮反推。
- Favorite、ViewHistory 扩展 beverageId；水果、调料继续复用 ingredientId。
- RecipeStep 明确 image/video/mediaType/duration/timerEnabled，添加菜谱、详情和烹饪模式共用一套 DTO。
- Recipe.visibility 使用枚举并在所有查询中强制执行，仅自己/家庭共享不能只靠前端标签。
- Ingredient.relatedRecipes 从自由 JSON 逐步转为可校验关系或后台选择器，避免无效跳转。

### E3. 后台配置调整

- 首页只保留有限模块模板：横向内容卡、知识图文卡、紧凑列表、主推荐卡，不继续堆相似模板。
- 分类页配置五大频道、二级分类、排序和卡片类型；C 端只消费配置，不在页面硬编码分类。
- 菜谱后台补齐步骤媒体、计时、份量和家庭提醒所需字段。
- 饮品后台按“基础饮品/可调制饮品”动态显示字段并做必填校验。
- 食材/水果/调料共用内容模型，但后台根据类型显示不同字段组。
- 上传中心明确：图片 JPG/PNG/WebP，视频 MP4/MOV；具体上限由产品与存储方案确认后统一写入前后端校验。

## 5. 推荐实施顺序

### 阶段 0：冻结原型与建立验收矩阵

- 把当前原型作为视觉与交互基线，不继续边开发边改信息架构。
- 为 393pt、375pt、430pt 和 100%/150%/200% 字体建立截图用例。
- 锁定首页 Banner 与详情页主图比例等已确认项。

### 阶段 1：先修基础设施和 P0 数据边界

- 真实鉴权、家庭共享菜篮、个人偏好、上传、饮品结构化 DTO。
- 建立 App Shell、统一状态组件、统一底部操作栏、统一详情页主图 Shell。

### 阶段 2：首页与分类

- 首页顶部保持已锁定结构，只替换推荐流组件。
- 合并分类实现，完成五频道与卡片规范。

### 阶段 3：五类详情与制作流程

- 菜谱详情 → 烹饪模式。
- 食材/水果/调料详情共用详情 Shell。
- 饮品详情 → 调制饮品制作模式。

### 阶段 4：家庭菜篮

- 家庭切换、食材/菜谱双视图、家庭口味、挑选面板、完成采购和采购历史。

### 阶段 5：我的与二级页面

- 我的、个人资料、我的菜谱、添加菜谱、收藏、浏览、家庭管理、通知、隐私、账号安全。

### 阶段 6：联调与验收

- 后台配置 → 后端落库 → C 端展示全链路。
- 正向、逆向、空态、错误、重复点击、权限、跨家庭隔离、断网、字体放大与安全区测试。

## 6. 第一批建议落地范围

第一批不要直接重写所有页面。建议只做以下四件事：

1. 修复家庭菜篮共享查询和真实身份校验方案。
2. 定义统一 App Shell、详情 Shell、状态组件和底部操作栏。
3. 将首页与分类拆出正式组件清单，确认 CMS 字段映射。
4. 选“首页推荐 + 分类 + 菜谱详情”三页做垂直样板，打通真实数据后再复制规范到其他页面。

这批完成后，再进入全页面迁移，风险最低。
